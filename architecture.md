The goal of this project is to create and host a web-based application similar to Dropbox which allows users to register accounts, upload, download and delete files  while being hosted on the AWS.  

Frontend 

 The technologies used for the front end include React and Vite, with Nginx serving the built application in its own Docker container. React is used to build the users interface while Vite provides the development server and builds the frontend into production files. Nginx is used to serve the frontend and forwards API requests to the backend. 

When the user visits the site the CloudFront forwards the request to the EC2 instance, Nginx serves the built React application to the browser, React then displays the application and handles user interactions. Whenever backend access is required the frontend is able to send an API request  to the backend and returns with the required data. 

In this version of the code there is 2 separate containers both frontend and backend, the frontend container works by using nginx to serve the production, listens on port 80, which is published to port 80 on the EC2 instance as well as sharing the dropbox network and forwarding the APIs. The frontend code folder is responsible for handling the APIs which allows for communication with the backend API as well as containing the components folder which is filled with reusable user interface components. The context folder contains shared application state using React Context.  

The frontend uses react router to handle navigations between pages as well as using react hook to form management and validation. Vite is used to handle the deployment it does this by building the frontend production files. These files are then served into the docker container by nginx as well as API requests. 

Backend 

The main purpose of the backend is to store and house structed information such as user data and uploads, these files are stored in the AWS S3 bucket while information such as user accounts and file names are stored in the RDS. The backend is built using node.js and express and is responsible for handling the application logic and processing the frontends requests, as well as handling user authentication and communications with the database and file storage services.  

In order to get the frontend to communicate with the backend we needed to use Ngnix to act as a reverse proxy as it makes communication between the front and the backend simpler as well as providing a production server, (A reverse proxy is a server that sits between clients and web servers, forwarding client requests to the appropriate backend server), without nginx we would not be able to serve files from the frontend to the backend and would require another web server to do so. How this works is when a user does an action such as uploading and API request is sent nginx picks up this request notices that its an API request and sends it to the backend container, the backend processes the request as sends it back through nginx. 

We use express to create our backend APIs when a request is forwarded to the backend express determines what should happen to it, such as creating new users or uploading files. 

The backend is also responsible for user authentication; user authentication is required in both the frontend and the backend because the frontend alone cannot dictate if a user is able to access data due it being more easily manipulated. 

The backend is stored on its own container separate from the frontend on port 3000, this is because it allows us to deploy and update the backend separate from the frontend to streamline production. In order for the backend to communicate with amazons RDS we created 5 parameters in the parameter store, these being DB_HOST which acts as an endpoint, DB_POST which gives it the port connection, DB_USER the database user name, DB_PASSWORD the database password and DB_NAME the database name,  When we deploy the backend, our deployment script retrieves these values from Parameter Store and passes them into the backend container as environment variables, these are then used to establish a MYSQL connection. Similarly, we created multiple permissions for the communication between the backend and S3, STORAGE_DRIVER=s3 was used to tell the backend to use S3 instead of the local storage, S3_BUCKET is used to identifies which S3 bucket to use and AWS_REGION identifies the AWS region. In order for the bucket to used our EC2 instance has a IAM role known as notes-app-containers-roles-ca1 

IAM roles 

AWS Identity and Access Management (IAM) is designed to allow users to securely control who has access to their site as well as what authorizations they are allowed to have. In our project we used 2 IAM roles these being notes-app-containers-roles-ca1 which is used to get our EC2 instance to access AWS services required to run the application, inside the role we given it access to the amazon ECR which allows it to download our front and backend images, the parameter store which retrives database credentials, the S3 which allows it to store files, the AWS system manager which allows for remote instance management and deployment commands as well as the CloudWatch. We also created the push-notes-app-role-ca1 which was used by our GitHub Actions workflow to publish Docker images and trigger deployments.  

In order for GitHub to access the IAM roles we must configure the OpenID connect or the OIDC which allows GitHub Actions to prove its identity to AWS without needing permanent access keys or passwords, When our deployment workflow runs, GitHub sends a temporary identity token to AWS. AWS checks this token to make sure the request is coming from an authorised GitHub workflow. If the checks are successful, AWS gives GitHub Actions temporary permission to use the IAM role. This allows our workflow to upload Docker images to Amazon ECR and deploy the application to EC2 using AWS Systems Manager. 

Parameter store 

The parameter store is an AWS service which allows us to store our configuration values needed to run the application. Instead of writing these values directly into our source code, we stored them in Parameter Store. We created eight parameters these being host, port, user, name, password, bucket, region and secret 

Containerisation and Docker 

In order to containerize our application, we needed to use docker which allowed us to package each part of the application's dependencies so that it can run on its own. Containerisation is a small standalone and runnable instance of a software application that contains all of an applications code and dependencies so it can run smoother. In our example we our backend requires the use of node.js and other dependencies without docker we would have to install and configure every single one of these dependencies separately and directly into our EC2 instance. In my project  i created 2 separate docker images one in the frontend and one in the backend, the one in the frontend contains the react application and the nginx, the one in the backend contains the node.js, express and backend dependencies. The images created are used to build 2 separate containers, we separated them because  it allowed for independent deployment as well as the separation of responsibilities. A Docker image is a read-only blueprint, template used to create Docker containers. It is a standalone, executable package that bundles together everything needed to run a piece of software while a container is a lightweight, portable, and self-contained unit that packages an application together with all its code. In order for our containers to communicate with one another we created a docker network called dropbox-network, we do this because we need to have the frontend running on port 80 and the backend on port 3000 this allows nginx to forward the API requests to the backend without exposing it to the public. 

GitHub actions 

GitHub actions are a set of tools built into GitHub which allows users automate tasks such as testing, in our example we used GitHub actions for the testing, building and deployment of our application. GitHub actions are important because without them every time we made a change in our code we would have to manually build the docker image and upload it to the ECR, GitHub actions allows us to automate this task. In order to get GitHub actions working we must first create a workflow folder inside the workflow is 3 separate files these being checks.yml which is used for running automated checks against our frontend and backend, publish.yml which builds the docker image and deploys them to the application, as well as the rollbacks.yml Allows us to manually restore a previous application version. The purpose of our contagious integration workflow also known as check.yml is to check our code for errors before deploying it, when we push to GitHub the CI automatically runs tasks such as Checking out the latest source code, Setting up Node.js version 24, Installing dependencies using npm CI, Running lint checks and Building the frontend production files. GitHub actions are important because if we didn't have them errors may be able to seep through the cracks and get into our code during the continuous integration, the GitHub actions catch this error before it is uploaded and cancels the upload.  

Rollback recovery 

A rollback is the process of restoring an earlier version of an application when a newer version causes problems. In my example i created 2 rollback methods automatic rollback which detects failed health checks and attempts to restore previous versions, as well as manual rollback which allows us to use our GitHub actions to restore a previous version whenever needed. I created a file known as deploy.sh which is designed to preform health checks after deploying new containers, it does this by checking if the backend and frontend are both responding if either fails the script attempts to restart the containers using older versions of the docker image. For the manual rollbacks we created a file called rollbacks.sh this allows us to manually rollback from GitHub actions by using specific git commands. 

Security groups 

A security group is a set of rules that determines what network traffic can enter or leave an AWS resource, security groups act as virtual firewalls that allow us to protect our application by only allowing in the necessary network connections. There are 2 types of rules in a security group inbound rules and outbound rules, inbound rules control which connection are allowed into a resource and outbound rules control which connections the resource can initiate to other destinations.  In my example I used security groups to control which network traffic is allowed to reach our AWS resources helping protect the application from unauthorised connections. I configured rules allowing HTTP traffic on port 80 and HTTPS traffic on port 443, allowing web requests to reach the instance. The security group also helps restrict access to other ports, such as the backend's port 3000, which does not need to be publicly accessible because the frontend and backend communicate through an internal Docker network.
